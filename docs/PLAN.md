# SpirChat — خطة المشروع والمقترحات الهندسية

> منصة تواصل "صامدة" تجمع بين المحادثات (مثل واتساب) والمنشورات والصور (مثل إنستغرام)،
> وتعمل عند انقطاع الإنترنت العالمي عبر: الإنترنت الداخلي، والخوادم المحلية، والواي فاي،
> والبلوتوث، والراديو بعيد المدى، وحتى "النقل اليدوي" للبيانات.

---

## ⭐ تحديث: القرارات بعد تحديد السياق

**السياق:** مشروع شخصي بحثي، والعراق هو البلد المستهدف، والجدول الزمني قصير، والبرمجة كلها يكتبها Claude.

### ما تغيّر في الخطة
1. **استبدال Rust بـ TypeScript في كل المشروع.**
   - البروتوكول والمحطة وتطبيق الويب كلها بلغة واحدة ومكتبة بروتوكول واحدة مشتركة.
   - هذا أسرع بكثير في التطوير.
   - المحطة تعمل على Node.js 22 مباشرة دون خطوة بناء، وقاعدة بياناتها SQLite المدمجة في Node.
   - التشفير بمكتبات noble (`@noble/curves` و `@noble/ciphers` و `@noble/hashes`). مكتوبة بـ JavaScript خالص، وخضعت لتدقيق أمني مستقل، وتعمل في المتصفح وفي Node.
   - يمكن إعادة كتابة النواة بـ Rust لاحقاً إن احتاج تطبيق أندرويد ذلك.
2. **المحطة + تطبيق الويب أولاً** (أُنجز النموذج الأول، انظر حالة التنفيذ أدناه). تطبيق أندرويد الأصلي مع البلوتوث يأتي بعده.
3. **لا جهة شريكة**، فلا توجد "جهة رسمية" تملك قناة الطوارئ. بدلاً من ذلك، كل مشغّل محطة يحدد بنفسه الهويات المسموح لها بنشر تنبيهات موثّقة (`ALERT_KEYS`)، مثل مسؤول الحي أو المستشفى القريب.

### خصوصيات العراق التي أُخذت بالحسبان
- **قطع الإنترنت الحكومي متكرر** (أيام الامتحانات الوزارية والاحتجاجات)، وأحياناً يشمل الشبكة الداخلية. لذلك لا يعتمد التصميم على أي خادم مركزي، ويبقى الإنترنت الداخلي طبقة اختيارية فقط.
- **انقطاع الكهرباء الوطنية يومي.** المحطة يجب أن تعمل على بطارية أو UPS، والتطبيق يجب أن يكون خفيفاً على بطارية الهاتف.
- **أندرويد هو الغالب** (أكثر من 80% تقريباً)، فتطبيق أندرويد الأصلي هو الخطوة التالية بعد الويب.
- **اللغة:** العربية أولاً، ونسخة بالإنجليزية جاهزة. **الكردية (السورانية والبهدينانية)** مطلوبة لإقليم كردستان، وتحتاج مراجعة من متحدث أصلي قبل اعتمادها.
- **الترددات:** استخدام الواي فاي (2.4/5GHz) والبلوتوث مسموح عموماً. أما **أجهزة LoRa** فيجب التحقق من النطاق المسموح ومن متطلبات هيئة الإعلام والاتصالات (CMC) قبل استيرادها أو تشغيلها.
- **الأمان:** البث اللاسلكي وتشغيل محطات اتصال مستقلة قد يكون حساساً قانونياً أو أمنياً في بعض الظروف. التطبيق يعرض تحذيراً واضحاً بذلك، والمحطة لا تسجّل أي بيانات شخصية.

## 0. الخلاصة التنفيذية (TL;DR)

1. **لا توجد تقنية واحدة تغطي دولة كاملة.** البلوتوث يغطي عشرات الأمتار، والواي فاي مئات الأمتار، والراديو (LoRa) كيلومترات لكن لرسائل نصية قصيرة جداً. الحل هو **شبكة متعددة الطبقات** يختار التطبيق فيها أفضل مسار متاح تلقائياً.
2. **النموذج الصحيح هو "خزّن ثم مرّر" (Store-and-Forward / DTN)** وليس "اتصال لحظي". الرسالة قد تصل خلال ثانية إذا وُجد مسار، أو خلال ساعات إذا انتقلت مع شخص يمشي من حي إلى آخر. التطبيق يجب أن يُصمَّم ليتقبّل هذا.
3. **أبدأ بالمحطة المحلية (Hub) وليس بالبلوتوث.** محطة Raspberry Pi + راوتر واي فاي تخدم مئات الهواتف فوراً، وتعمل على **أي هاتف (أندرويد وآيفون) عبر المتصفح** دون تثبيت شيء. هذه أسرع قيمة حقيقية يمكن تقديمها.
4. **الصور والفيديو لا تُنشر عبر البلوتوث.** شبكة الـ Mesh تنقل النصوص والصور المصغّرة فقط؛ الصور الكاملة تُنقل عبر الواي فاي والمحطات.
5. **أندرويد أولاً.** نظام iOS يقيّد البلوتوث في الخلفية ولا يدعم Wi-Fi Direct، فلا يمكن للآيفون أن يكون "عُقدة ترحيل" موثوقة. الآيفون يُخدم عبر المحطات (Web App) أولاً.
6. **الأمان ليس ميزة إضافية بل شرط للبقاء.** في سياق حرب، الهوية والموقع والبيانات الوصفية (من يتحدث مع من) قد تعرّض حياة الناس للخطر.

## 1. ملاحظات نقدية على المقترحات السابقة

| المقترح | تقييمي |
|---|---|
| **Briar** | ممتاز أمنياً ومرجع جيد للبروتوكول، لكنه مصمم لمحادثات بين جهات اتصال معروفة، ولا يدعم شبكة Mesh متعددة القفزات بين غرباء، وكوده Java ثقيل للتعديل. **أنصح بدراسته لا بتفريعه (Fork).** |
| **Manyverse / SSB** | فكرة "سجل منشورات موقّع يتزامن بين الأجهزة" هي بالضبط ما نحتاجه للجزء الشبيه بإنستغرام. لكن بروتوكول SSB نفسه قديم وبطيء في المزامنة الأولية، والمشروع توقف تطويره عملياً. **نأخذ الفكرة ونبني نسخة أخف.** |
| **Matrix** | ممتاز إذا كان هناك خادم متاح دائماً (طبقة الإنترنت الداخلي)، لكنه ثقيل على Raspberry Pi ولا يعمل بين هاتفين بلا خادم. يمكن إضافته لاحقاً كجسر (Bridge) اختياري. |
| **Bridgefy** | تجنّب تقليد تصميمه؛ نُشرت أبحاث أمنية (2020–2021) أثبتت ثغرات خطيرة فيه تتيح تتبع المستخدمين وانتحال الهوية. |
| **"إشارة تُلتقط وتُوزَّع على هواتف الدولة"** | الهاتف لا يستطيع بث إشارة لمسافات بعيدة. التغطية الواسعة تأتي من **عدد كبير من العُقد** + **محطات بهوائيات قوية** + **روابط بعيدة المدى بين المحطات**، وليس من هاتف واحد. |

## 2. المعمارية المقترحة: خمس طبقات اتصال

```
                 ┌──────────────────────────────────────────────┐
  الطبقة 4       │  الإنترنت الداخلي للدولة (Domestic Intranet)    │  تغطية: الدولة كاملة
  (إن وُجد)      │  محطات مركزية في مراكز بيانات داخل البلد         │
                 └───────────────▲──────────────────────────────┘
                                 │  مزامنة بين المحطات
                 ┌───────────────┴──────────────────────────────┐
  الطبقة 3       │  روابط بعيدة بين المحطات                        │  تغطية: 5–50 كم/رابط
                 │  واي فاي نقطة-لنقطة (هوائيات اتجاهية) + LoRa     │
                 └───────────────▲──────────────────────────────┘
                 ┌───────────────┴──────────────────────────────┐
  الطبقة 2       │  محطات الأحياء (Hubs): Raspberry Pi + راوتر     │  تغطية: 100 م – 2 كم
                 │  تخدم التطبيق + نسخة ويب لأي متصفح              │
                 └───────────────▲──────────────────────────────┘
                 ┌───────────────┴──────────────────────────────┐
  الطبقة 1       │  هاتف ↔ هاتف: BLE + Wi-Fi Direct/Aware + LAN    │  تغطية: 10–100 م/قفزة
                 │  (Mesh + خزّن ثم مرّر)                          │
                 └───────────────▲──────────────────────────────┘
                 ┌───────────────┴──────────────────────────────┐
  الطبقة 0       │  "ناقلو البيانات" (Data Mules)                  │  تغطية: أي مسافة، بتأخير
                 │  هواتف/حافلات/سيارات أجرة/فلاشات USB            │
                 └──────────────────────────────────────────────┘
```

### ملاحظة مهمة عن الطبقة 4
في حالات **قطع الكابلات البحرية الدولية** غالباً ما تبقى الشبكة الداخلية للدولة (شركات الاتصالات ونقاط تبادل الإنترنت المحلية IXP) تعمل. لذلك: محطة SpirChat مستضافة في مركز بيانات **داخل البلد** قد تصل إلى كل مستخدمي الإنترنت والبيانات الخلوية في الدولة فوراً. هذه أوسع تغطية ممكنة بأقل جهد، ويجب أن يحاول التطبيق الوصول إليها أولاً. أما في حالة **الإغلاق المتعمد** من السلطات، فتسقط هذه الطبقة ونعتمد على الطبقات 0–3.

### كيف يختار التطبيق المسار؟
كل رسالة تُوضع في "صندوق صادر" محلي، ويحاول التطبيق تسليمها عبر أي قناة متاحة بالترتيب:
`محطة عبر الإنترنت الداخلي ← محطة عبر الواي فاي المحلي ← هاتف قريب (Wi-Fi Direct) ← هاتف قريب (BLE)`
ولا تُحذف من الصندوق حتى يصل إشعار استلام أو تنتهي صلاحيتها (TTL).

## 3. مقترحاتي الخاصة (ما يميّز SpirChat)

### 3.1 المحطة كـ "بوابة مقيدة" (Captive Portal) — أهم مقترح
عند اتصال أي شخص بشبكة الواي فاي `SpirChat-<اسم الحي>`، تفتح صفحة تلقائياً فيها:
- نسخة ويب كاملة من المنصة (PWA) تعمل على **أي هاتف بما فيه الآيفون** دون تثبيت.
- زر لتحميل ملف APK لتطبيق أندرويد مباشرة من المحطة.

هذا يحل مشكلتين: الوصول للآيفون، وتوزيع التطبيق حين تكون متاجر التطبيقات غير متاحة.

### 3.2 التطبيق ينشر نفسه (Viral Distribution)
بما أن Google Play لن يعمل بدون إنترنت، يحتوي التطبيق على زر "شارك التطبيق" يرسل ملف APK إلى هاتف آخر عبر الواي فاي/البلوتوث أو يعرض QR يفتح صفحة تحميل محلية. مع **توقيع رقمي للتحديثات** حتى لا تنتشر نسخ معدّلة خبيثة.

### 3.3 قناة الطوارئ الموقّعة
قناة خاصة للدفاع المدني / الهلال الأحمر / المستشفيات: رسائلها موقّعة بمفاتيح موثوقة مُضمَّنة في التطبيق، ولها **أعلى أولوية** وتنتشر لكل الأجهزة (Flooding)، وتظهر بشارة "موثّق". تحل مشكلة الشائعات والأخبار الكاذبة وقت الأزمات.

### 3.4 زر الاستغاثة (SOS)
رسالة قصيرة جداً (< 200 بايت): الهوية + نوع الحالة + موقع تقريبي اختياري. أعلى أولوية في كل الطبقات، وصغيرة بما يكفي لتمر عبر LoRa.

### 3.5 نظام أولويات صارم للبيانات
عرض النطاق في الـ Mesh ضئيل جداً، فيجب أن يُقسَّم:

| الأولوية | النوع | الحد الأقصى للحجم | عبر BLE؟ | عبر LoRa؟ |
|---|---|---|---|---|
| 0 | SOS + قناة الطوارئ | 200 بايت | ✅ | ✅ |
| 1 | رسائل نصية خاصة | 4 KB | ✅ | ✅ (مقتطعة) |
| 2 | رسائل المجموعات | 4 KB | ✅ | ❌ |
| 3 | منشورات نصية + صورة مصغّرة | 20 KB | ✅ | ❌ |
| 4 | صور كاملة (مضغوطة WebP/AVIF) | 150 KB | ❌ (Wi-Fi Direct فقط) | ❌ |
| 5 | رسائل صوتية (Opus 8–16kbps) | 100 KB | ❌ | ❌ |
| 6 | فيديو قصير | 2 MB | ❌ (محطات فقط) | ❌ |

### 3.6 "الخلاصة المحلية" بدل الخلاصة العالمية
الجزء الشبيه بإنستغرام يجب أن يكون **محلياً بطبيعته**: منشورات الحي، منشورات من تتابعهم، والقناة الرسمية. لا يمكن (ولا يجب) أن تنتشر كل صورة لكل هاتف في الدولة. المحطات تحتفظ بالصور الكاملة، والهواتف تحمل المصغّرات فقط إلى أن يطلب المستخدم الصورة الكاملة.

### 3.7 الهوية بلا رقم هاتف
- الهوية = زوج مفاتيح يُولَّد على الجهاز (Ed25519). لا رقم هاتف، لا بريد، لا خادم تسجيل.
- إضافة جهة اتصال عبر **مسح رمز QR** وجهاً لوجه (أعلى ثقة) أو عبر المحطة.
- "رقم أمان" للتحقق من الهوية كما في Signal.

### 3.8 ميزات حماية المستخدم في سياق حرب
- قفل بـ PIN، و**PIN إكراه** يفتح نسخة فارغة.
- زر **مسح فوري** لكل البيانات.
- خيار إخفاء أيقونة التطبيق (تمويه كتطبيق آلة حاسبة).
- تحذير صريح داخل التطبيق: **أي بث لاسلكي (بلوتوث/واي فاي/راديو) يمكن رصد مكانه** بأجهزة تحديد الاتجاه، مع وضع "صامت" يوقف كل البث.
- عدم إرفاق الموقع الجغرافي افتراضياً، وإزالة بيانات EXIF من الصور تلقائياً.

### 3.9 الحماية من الإغراق والرسائل المزعجة
لا يوجد خادم مركزي يحظر أحداً، لذلك:
- حد أقصى للرسائل لكل هوية في الساعة تفرضه كل عقدة ترحيل.
- "إثبات عمل" (Proof-of-Work) خفيف على الرسائل العامة لجعل الإغراق مكلفاً.
- أولوية ترحيل أعلى لرسائل الهويات الموثوقة (جهات اتصالك ومن يثقون بهم).

## 4. التصميم التقني

### 4.1 المكدس التقني المقترح

> **ملاحظة:** هذا هو المقترح الأصلي. اعتُمد بدلاً منه مكدس TypeScript موحّد لتسريع التنفيذ (انظر «التحديث» في أعلى الملف).

| المكوّن | التقنية | السبب |
|---|---|---|
| **النواة (Core)**: التشفير، صيغة الرسائل، المزامنة، التخزين | **Rust** | مكتبة واحدة تُستخدم في أندرويد + iOS + المحطة + سطح المكتب. آمنة للذاكرة وسريعة وموفرة للبطارية. تُربط بالمنصات عبر UniFFI. |
| **تطبيق أندرويد** | **Kotlin + Jetpack Compose** | وصول كامل للـ BLE و Wi-Fi Direct و Wi-Fi Aware وخدمات الخلفية — وهذا ما لا توفره الأطر متعددة المنصات بشكل موثوق. |
| **تطبيق iOS** (لاحقاً) | Swift + SwiftUI | نفس نواة Rust. يعمل كعميل للمحطات أكثر منه كعقدة ترحيل. |
| **برنامج المحطة (Hub)** | **Rust** (ملف تنفيذي واحد) + SQLite | يعمل على Raspberry Pi أو راوتر OpenWrt أو أي حاسوب. بلا قواعد بيانات خارجية. |
| **نسخة الويب (PWA)** | TypeScript + Preact/Svelte + نواة Rust مترجمة لـ WebAssembly | خفيفة جداً، تُخدَّم من المحطة، وتعمل بلا إنترنت بعد التحميل الأول. |
| **جسر LoRa** | دعم أجهزة **Meshtastic** الجاهزة عبر BLE/Serial | أجهزة رخيصة (~25–40$) بمدى عدة كيلومترات، ومجتمع مفتوح المصدر قائم. |

> **لماذا لا Flutter أو React Native؟** يمكن استخدامهما للواجهة، لكن كل منطق الشبكات اللاسلكية سيُكتب بلغة أصلية (Native) على أي حال. البدء بـ Kotlin يقلل طبقات التعقيد. إذا كان فريقك يتقن Flutter فهو خيار مقبول للواجهة مع نفس نواة Rust.

### 4.2 نموذج البيانات
كل شيء في SpirChat هو **"ظرف" (Envelope)** موقّع وغير قابل للتعديل، ومعرّفه هو بصمة محتواه (Content-Addressed):

```
Envelope {
  id:         BLAKE3(header || payload)     // معرّف = بصمة المحتوى
  version:    u8
  kind:       DirectMessage | GroupMessage | Post | Media | Receipt | SOS | Alert
  priority:   0..6
  created_at: timestamp
  expires_at: timestamp                      // TTL: يُحذف بعده من عقد الترحيل
  hop_limit:  u8                             // عدد القفزات المتبقية
  recipient:  routing_tag                    // وسم مُعمّى، لا يكشف هوية المستلم
  payload:    encrypted bytes
  signature:  Ed25519                        // داخل الحمولة المشفرة للرسائل الخاصة
}
```

- **الرسائل الخاصة**: مشفرة للمستلم فقط (X25519 + XChaCha20-Poly1305)، وهوية المرسل **داخل** التشفير (Sealed Sender)، فالوسيط لا يعرف من أرسل ولا محتوى الرسالة.
- **المنشورات العامة**: موقّعة وغير مشفرة، مرتبطة في **سجل خاص بكل مستخدم** (Append-only Feed) كفكرة SSB.
- **المجموعات**: مفتاح مجموعة متماثل يُدار بالبروتوكول MLS (أو نسخة مبسطة منه في المرحلة الأولى).

### 4.3 بروتوكول المزامنة
عندما يلتقي جهازان (هاتف-هاتف أو هاتف-محطة):
1. مصافحة مشفرة (Noise Protocol XX).
2. **مطابقة المجموعات** (Range-Based Set Reconciliation) لمعرفة أي الظروف لدى أحدهما وليست لدى الآخر، بأقل قدر من البيانات المتبادلة.
3. تبادل الظروف المفقودة **حسب الأولوية**، مع حد زمني لكل لقاء.

### 4.4 التوجيه (Routing)
- **المرحلة الأولى**: انتشار وبائي محدود (Epidemic Routing) مع `hop_limit` و `TTL` وحصص تخزين.
- **المرحلة اللاحقة**: توجيه احتمالي (PRoPHET / Spray-and-Wait) يتعلم أي الأجهزة تلتقي بالمستلم غالباً، لتقليل الهدر.
- الرسائل الموجهة لمستخدم مسجّل في محطة معروفة تُرسل إلى تلك المحطة عبر شبكة المحطات.

### 4.5 البطارية
- مسح BLE بنظام دوري متكيّف: مكثف عند الشحن أو عند وجود رسائل معلقة، ومتباعد (كل 5–15 دقيقة) عند البطارية المنخفضة.
- Wi-Fi Direct يُفعّل فقط عند وجود بيانات كبيرة للنقل.
- "وضع الصمود" عند بطارية أقل من 15%: نصوص وSOS فقط.

## 5. خارطة الطريق (Roadmap)

### المرحلة 0 — الأساسات (3–4 أسابيع)
- [ ] تحديد صيغة الظرف (Envelope) ومواصفات البروتوكول v0 في `docs/protocol.md`.
- [ ] مكتبة Rust للنواة: المفاتيح، التشفير، التوقيع، التخزين في SQLite.
- [ ] نموذج أولي لمزامنة جهازين عبر TCP في شبكة محلية.
- [ ] اختبارات وحدة + محاكي شبكة بسيط لعشرات العقد الافتراضية.

### المرحلة 1 — المحطة + نسخة الويب (6–8 أسابيع) ⭐ أول إصدار قابل للاستخدام
- [ ] خادم المحطة على Raspberry Pi: محادثات، مجموعات، منشورات، رفع صور مضغوطة.
- [ ] نسخة ويب PWA تُخدَّم من المحطة عبر Captive Portal.
- [ ] صورة نظام جاهزة (Image) للحرق على بطاقة SD: "شغّل واتصل".
- [ ] دليل تركيب المحطة بالعربية.
- **النتيجة**: حي كامل يستطيع التواصل بالنص والصور بلا إنترنت، من أي هاتف.

### المرحلة 2 — تطبيق أندرويد + Mesh (8–12 أسبوعاً)
- [ ] تطبيق أندرويد بواجهة عربية (RTL) أولاً: محادثات، خلاصة، جهات اتصال QR.
- [ ] نقل هاتف-هاتف عبر BLE (نصوص ومصغّرات).
- [ ] نقل عبر Wi-Fi Direct / Wi-Fi Aware للصور.
- [ ] خدمة خلفية للترحيل مع إدارة البطارية.
- [ ] مزامنة تلقائية مع المحطة عند الاقتراب منها.
- [ ] مشاركة التطبيق من هاتف لهاتف.

### المرحلة 3 — شبكة المحطات (6–8 أسابيع)
- [ ] مزامنة محطة-محطة عبر أي رابط IP (إنترنت داخلي، واي فاي بعيد المدى).
- [ ] دليل لربط المحطات بهوائيات اتجاهية (5–30 كم).
- [ ] وضع "ناقل البيانات": تصدير/استيراد حزمة بيانات عبر USB أو هاتف.
- [ ] قناة الطوارئ الموقعة.

### المرحلة 4 — المدى البعيد و iOS (8+ أسابيع)
- [ ] جسر Meshtastic/LoRa للنصوص وSOS.
- [ ] تطبيق iOS (عميل للمحطات + تبادل محدود مع أجهزة قريبة).
- [ ] رسائل صوتية مضغوطة.

### المرحلة 5 — التجربة الميدانية والتدقيق
- [ ] تجربة في حي أو جامعة: 3–5 محطات و100–500 مستخدم.
- [ ] قياس: زمن التسليم، نسبة الوصول، استهلاك البطارية.
- [ ] **تدقيق أمني خارجي مستقل** قبل أي توصية باستخدامه في ظروف خطرة حقيقية.

## 9. الخطوة التالية

1. تثبيت التطبيق على هاتفين وتجربة الاتصال المباشر بينهما (انظر README).
2. تجربة المحطة على Raspberry Pi حقيقي (انظر [دليل التركيب](hub-setup-ar.md)).

### قرارات تقنية في تطبيق أندرويد
- **Google Nearby Connections:** يختار تلقائياً بين البلوتوث و BLE و Wi-Fi Direct، ويوفّر أسابيع من العمل.
  - **عيبه:** يحتاج خدمات Google Play، فلا يعمل على هواتف هواوي الحديثة.
  - **البديل لاحقاً:** طبقة BLE و Wi-Fi Direct مكتوبة يدوياً.
- **منطق المزامنة كله في JavaScript،** وطبقة أندرويد تنقل النصوص فقط. لذلك يُختبر المنطق في المتصفح دون هاتف.
- **حدود حالية:**
  - الاتصال بين الهواتف يعمل فقط والتطبيق مفتوح.
  - كل بناء على GitHub موقّع بمفتاح مختلف، فتحديث التطبيق يتطلب حذف النسخة القديمة أولاً، وهذا يمسح البيانات. احفظ رمز الاستعادة قبل الحذف.
